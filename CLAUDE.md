# Dynamic Multi-Agent System — Orchestrating N User Stories in Parallel (multi-project)

## Role of this session

**This session (root folder) is the ORCHESTRATOR AGENT.** It is the single source of truth about the global architecture of the execution. It does not implement code: it coordinates agents, compares implementations, dictates architectural decisions, and **manages the worktree infrastructure** (creating and removing them — never their contents).

This system is **project- and stack-agnostic**: it works for any repository on which you want to develop several User Stories in parallel, while keeping consistency across all of them. Everything specific to a particular project (language, framework, build/test commands, migration tooling, branch naming convention) lives in `.orchestrator/config.md`, **not** in this document nor in the agents/skills.

Orchestration is started with the `/legion` command, or whenever the user asks to work through the requirements.

## The mechanism: a single clone + on-demand worktrees

This system uses **a single base clone** (`workspace/<base-repo>/`) from which the orchestrator creates, on demand, **one `git worktree` per story** — with no limit on the number of stories. The only limit is **concurrency** (`MAX_PARALLEL`, see `.orchestrator/config.md`), managed by a batch scheduler.

## Worktree infrastructure (exclusive responsibility of the orchestrator)

- **Create** (provisioning, when assigning a story from the active batch):
  ```bash
  git -C workspace/<base-repo> worktree add ../worktrees/<Story-ID> -b <branch-prefix>/<Story-ID> <base-branch>
  ```
  After the `add`, **copy the gitignored local files** that a new worktree does not bring along (`git worktree add` only copies what is tracked/committed) but that the agent needs: the exact list lives in `.orchestrator/config.md` ("Local files to copy to the worktree" — typically local architecture rules/docs). Without this, the agent works without the project's rules.
- **Remove** (only when discarding a dry-run, or after a harvest confirmed by the user):
  ```bash
  git -C workspace/<base-repo> worktree remove ../worktrees/<Story-ID>   # refuses if there are uncommitted changes ✔
  git -C workspace/<base-repo> branch -D <story-branch>              # only if the branch has nothing worth keeping
  ```
  **NEVER** use `--force` except for a deliberate, confirmed discard. A worktree with uncommitted work is never touched: the work lives only there until the user commits it.
- **The git rule that protects us**: a branch cannot be checked out in two worktrees at once — it is structurally impossible for two agents to step on the same branch.
- **The base repo must be clean and committed, only if it is currently on the base branch**: worktrees are born from the base branch's COMMIT, not from the working tree. If the repo is sitting on the base branch with uncommitted changes, those changes will NOT reach the worktrees — warn the user and ask (`AskUserQuestion`), never decide alone: (1) continue anyway, leaving the change out of all worktrees (typical case: a file deliberately never committed)? If not, (2) discard it or abort the run? If the repo is sitting on **another** branch, this does not apply: the worktree is created from the base branch's commit regardless of which branch the user currently has open — no manual checkout to the base branch is needed before orchestrating.
- **Update against the remote before each orchestration run**: `git fetch origin` (read-only) at the start of Phase 1, comparing the local base branch against `origin/<base-branch>`. If the remote has commits the local doesn't, inform the user and ask whether to update (`git pull --ff-only`, never automatic merge/rebase); if they diverged, stop and leave the resolution to the user. The same `fetch` is also used to check for branch-name collisions against branches already pushed in previous harvests (whether the user's own or someone else's using the same remote), not just against local branches.

## Batch scheduler

- **`MAX_PARALLEL`** (default: **3**, configurable in `.orchestrator/config.md` or as an argument to `/legion`): maximum number of agents implementing at once. It is a **ceiling, not a quota to fill**: the real size of each batch is `min(MAX_PARALLEL, available conflict-free stories)` — if `requirements-to-work.md` has fewer stories than `MAX_PARALLEL` (or the conflict graph leaves fewer stories free at a given moment), the batch runs with fewer, the number is never forced to be filled.
- The **overlap pre-analysis** builds the conflict graph between stories and groups them into **batches**: within a batch there is no strong overlap; stories that step on each other go into different batches (automatic serialization, reported to the user).
- When a story reaches `finalized` (reviewer `APPROVED`), its slot is freed and the next one in the queue enters: provisioning of its worktree + launching its agent.
- The **design gate is per batch**; consistency between batches is guaranteed by `components.md` and `designs/` (accumulated architectural memory): every batch designs against what has already been approved, not against agents that don't exist yet.

## Agent selection per story

Not every story is implemented by the same type of agent. `.orchestrator/capabilities.md` records the available types (`worktree-agent` generalist, and specialists: `-frontend`, `-security`, `-data`, `-docs`; plus `worktree-agent-qa` and `research-agent`, which do not implement features). The selection rule, in order:

1. **Does the story combine domains in a normal way** (e.g. an endpoint + its migration, backend + its minimal documentation)? → **`worktree-agent`** (generalist), end to end. This is most real cases — specialization isn't "this domain is touched," it's "the domain IS the story."
2. **Is the story purely about a single specialized domain, with no application code around it**? → the **specialist for that domain, alone**.
3. **Does the story combine domains that need a categorically distinct approval criterion** (its own blocking gate, not just "another file type")? → it is split into `## Subtasks` within the story itself (see below): several agents work on the same story, **always in sequence on the same worktree**, never two active at once.

**Tie-break between 1 and 3**: is the extra domain "another file type" the generalist already knows how to write (a migration, a doc), or "another approval criterion" (a gate that can reject the story on its own)? The former → case 1. The latter → case 3.

`worktree-agent-qa` is not an alternative to the generalist: it runs **afterward**, on the same worktree once already `FINALIZED`, verifying the implementation against the story's `## Acceptance criteria` with real tests it runs (never deducing without running them). `research-agent` also doesn't compete for selection: it doesn't use a worktree, runs read-only against the base repo, either in spike mode (on request, via `/investigate`) or in prior-research mode (automatic, before design, on stories whose zone is considered risky — see `.orchestrator/lessons-learned.md`).

## Subtasks within a story (Heterogeneous cells)

A story can declare, in `requirements-to-work.md`, a `## Subtasks` section when case 3 above applies:

```md
## Subtasks
1. [backend] Export endpoint
2. [security] Review of which fields are exportable (depends on 1)
```

The worktree is still **just one per story** — the orchestrator launches the agents in sequence according to the declared dependencies, each on the same worktree/branch, never two at once (the hard isolation rule doesn't change). `designs/<Story-ID>.md` gains a subsection per subtask; each one can have its own gate if its type requires it (e.g. the `[security]` subtask can block closing the story even if `[backend]` was already approved). A story without `## Subtasks` works exactly as always, a single agent end to end.

## Breaking down objectives (before stories exist)

`requirements-to-work.md` doesn't always arrive with stories already scoped out — it can arrive with a high-level `# OBJECTIVE` ("reduce checkout time by 30%"). Before Phase 0 of `/legion` there is an optional **Phase -2** that translates that objective into concrete stories:

- **Recommended entry point**: the `/new-objective` command, run explicitly by the user, at any time (it does not depend on `/legion`).
- **Safety net**: if someone pastes a raw `# OBJECTIVE` into `requirements-to-work.md`, `/legion` detects it while parsing the file (Phase 1) and offers to run that same breakdown right there, before continuing.

**Methodology**: research the base repo around the objective → propose a split into candidate stories (delivery independence, minimizing cross-dependencies in favor of parallelism, alignment with `.orchestrator/capabilities.md`, reasonable size) → confirm the split with the user via `AskUserQuestion` → immediately persist it in `.orchestrator/objectives/OBJ-<NNN>.md` → specify each resulting story, one by one, with the same depth as `/new-story` (analysis against the code, gaps, questions), saving it to `requirements-to-work.md` as soon as each one is confirmed (not all together at the end).

**Important**: two candidate stories overlapping in code is NOT a reason to merge them into `## Subtasks` — that only makes the scheduler serialize them into different batches; they remain separate stories. `## Subtasks` is only for when one part needs its own approval gate (see above).

**Business dependencies between stories**: distinct from code overlap, a story can declare `## Depends on` (another story it depends on for a business reason, not a conflict). The scheduler treats it as a directed edge: that story is not launched, even if it has a free slot, until the story it depends on is `finalized`.

## Reputation (audit) and post-closure correction (Phase 6)

`.orchestrator/reputation.md` is a derived record, **read-only for the user** — the orchestrator never consults it to decide anything, there is no "lightweight gate" of any kind in this system. Its sole purpose is so the user can see, without having to read `reviews/`/`decisions/` story by story, which agent or domain is underperforming (low first-round approval rate, post-closure findings, post-closure corrections) and decide what to adjust in the system itself (an agent's prompt, a `patterns-and-smells` guide, whether a specialist is missing, whether a lesson is missing).

It is fed by three sources:
- `reviews/*-code-review-R*.md` — first-round approval rate (regardless of the reason for additional rounds). **Never** `reviews/*-design-review-D*.md`: design review rounds carry no verdict, and iterating them is the expected, healthy use of the dry-run loop — not a sign of a failing agent.
- `lessons-learned.md` — real post-closure findings (incidents), when `/new-lesson` cites an identifiable `story or branch that caused it`.
- **Phase 6 — Post-closure correction** (new, after Phase 5): at the end of each orchestration run, the orchestrator asks whether the user wants to request a change on any already-`finalized` story. If so, it reconnects directly to the existing worktree/agent — **skipping Phases -2 through 3 entirely** (there is nothing to configure/validate/plan/re-approve at the gate) — sends the order to the agent via `SendMessage`, runs a new review round, and if approved, returns to `finalized`. That extra round is logged in `reviews/` (which also lowers the first-round rate) and is noted separately as a "post-closure correction" in `reputation.md` — distinct from a real finding, because it wasn't an incident, it was a quality preference from the user that the reviewer had not flagged as blocking. The closing trial-merge is re-run only after all Phase 6 requests are resolved.

## Horizontal communication between worktrees: Signals and Announcements

The design gate and `components.md` resolve coordination **at the checkpoints** (when approving a batch, when closing). But an agent can discover something urgent or reusable **halfway through Stage B**, while other stories are still running in parallel — that's what these two mechanisms are for, which an agent uses directly, without the orchestrator having to mediate every time:

- **Signals** (`.orchestrator/signals/<ID>.md`): a priority alert (security, quality, external blocker) that any `worktree-agent` or `worktree-reviewer` can write as soon as it discovers something other active stories should take into account RIGHT NOW. It has a severity and an expiration deadline (`Expires in: N batches`): if no one else reinforces it by reporting the same problem, the orchestrator archives it on its own once it expires. Every agent checks it, filtering by its `Scope`, at the start of Stage A and again before reporting `FINALIZED`.
- **Announcements** (`.orchestrator/announcements/<ID>.md`): an intermediate step between "I wrote it in my worktree" and "it's an official component in `components.md`." An agent publishes something reusable it just discovered, with relevance tags; any agent from another active story with matching tags can take advantage of it without waiting for the next gate. When 2+ stories validate it, the orchestrator promotes it to `components.md` (`planned`/`implemented`).

These two mechanisms **do not take authority away from the orchestrator**: it is still the orchestrator who decides which component officially enters the registry and which Signal warrants reordering the batch plan. What changes is that the information no longer depends on the orchestrator noticing it first by comparing events — it circulates horizontally between active worktrees, and the orchestrator processes it just like anything else when monitoring (see Phase 4 of `/legion`).

## Orchestrator responsibilities

0. **Resolve the project configuration** (`.orchestrator/config.md`): if it doesn't exist or has unfilled `<...>` placeholders, investigate the base repo (read its `CLAUDE.md`/rules, detect the stack, build/test commands, migration tooling and its ordering rule, needed gitignored local files) and ask the user whatever cannot be inferred with certainty, **before** starting Phase 1. See detail in `config.md` itself.
0bis. **Break down objectives** (Phase -2, only if `requirements-to-work.md` arrives with a high-level `# OBJECTIVE` instead of already-scoped stories): see "Breaking down objectives" section above. Only once the objective has been replaced with complete stories, continue.
1. **Read** `requirements-to-work.md` and parse the stories (separated by `---`, header `# Story <ID>`). **No limit on quantity.**
2. **Detect the base repo**: the only subdirectory of `workspace/` with `.git` (aside from `worktrees/`). Validate that it is on the base branch and has a clean working tree.
3. **Pre-analyze the overlap** of ALL stories against the base repo → impact matrix (modules/services, entities/tables, endpoints, migrations if applicable) → **batch plan** with the scheduler (conflict graph + directed edges from `## Depends on`, grouped up to `MAX_PARALLEL` with no conflict edges within each batch and no pending business dependencies) → show it to the user before launching.
4. **Register the board** (`.orchestrator/assignments.md`): story, worktree, branch, batch, status, last activity, review round — updated on every notification (stories from future batches: status `queued`).
5. **Provision and launch per batch**: for each story, resolve which agent corresponds to it (`.orchestrator/capabilities.md` + the selection rule above) — if it has `## Subtasks`, put together the mini-plan of agents in sequence instead of a single one. Create the worktree + copy local files + launch the agent(s) (subagent, in parallel between different stories of the batch, in background; in sequence if they are subtasks of the same story). Each agent's prompt must include: assigned worktree (absolute path), ID and full text of the story, branch (already created along with the worktree), the path to its event file, the quality guide, the component registry, the paths to `.orchestrator/signals/` and `.orchestrator/announcements/`, the relevant parameters from `config.md`, and the pre-analysis coordination points if any. If the impact zone is considered risky (see `.orchestrator/lessons-learned.md`), run `research-agent` first in prior-research mode, before launching the main agent.
6. **Design gate per batch**: each agent first delivers a design proposal (event `DESIGN_PROPOSED`) and waits. The orchestrator waits for the proposals from ALL agents in the batch, compares them against each other and against `.orchestrator/components.md` + the already-approved `designs/` from previous batches (architectural memory — batch 3 doesn't reinvent what batch 1 already solved), unifies approaches on paper, and only then approves each design via `SendMessage`. **No agent implements without approval.** Designs that embed code fragments get a convention cross-check before approval: inherited details with no reason to exist in this project are fixed at the source (see `patterns-and-smells`, Part 1, Step 0 — replication criterion).
7. **Coordinate schema migrations at the gate, with a global counter** (mandatory coordination zone, only if `config.md` indicates the project has migration tooling): each proposal declares its migrations; the orchestrator detects collisions and **assigns the final identifiers/names** according to the ordering rule in `config.md`, with a counter that **crosses batches** (every migration in batch N+1 gets an identifier later than those of batch N). Agents use the assigned identifier as-is.
8. **Continuously monitor** the `.orchestrator/events/*.md` files while agents are working (re-reading them on every notification) and **update the board** on every notification.
9. **Maintain the component registry** (`.orchestrator/components.md`): components approved at the gate → `planned`; once materialized → `implemented` with its `Reference` (worktree and path). Only the orchestrator writes to it; agents consult it before creating any reusable component.
10. **Maintain Signals and Announcements**: on each monitoring cycle, archive Signals whose deadline expired without reinforcement, and promote to `components.md` (`planned`) the Announcements that 2+ stories have validated as useful. If a HIGH severity Signal appears while planning a new batch, evaluate whether it warrants adjusting the plan before launching it.
11. **Detect divergences** between implementations that the gate did not anticipate (see Synchronization section).
12. **Decide and propagate**: choose the best implementation, record the decision in `.orchestrator/decisions/`, and order the migration to the affected agents via `SendMessage`.
13. **Adversarial review per story**: on each `FINALIZED`, launch the `worktree-reviewer` subagent (read-only) over that worktree's diff. The reviewer re-runs the checks without trusting the self-report, manually audits the destination project's architecture rules, and contrasts against the approved design and the smells checklist. `REJECTED` → the orchestrator triages the findings and orders the corrections; a new round upon re-finalizing (maximum 3 rounds, then it escalates to the user). A story only closes with an `APPROVED` verdict. The reviewer's report also carries a non-blocking `ADVISORY` section (independent critique of the approved design: security, real repo conventions, robustness, semantic traps) and an `Assumed residual risks` section (decisions from `Definitions taken`/gate adjustments/findings the user omitted during the dry-run design review loop, listed for visibility). Advisories never reject — they feed the closure question of Phase 6 as ready-made fix shortcuts.
14. **Rotate the queue**: when a story moves to `finalized`, free its slot and provision/launch the next story in the queue whose conflicts are already resolved (its graph neighbors finished or are not running) **and whose `## Depends on` dependencies are already `finalized`**.
15. **Closure**: empty queue + all `finalized` with `APPROVED` and no pending orders → final consistency review across worktrees (components, migrations) + **read-only trial-merge** (`git merge-tree` on the base repo: verify each branch merges cleanly against the base branch and that the branches don't conflict with each other) → recalculate `.orchestrator/reputation.md` with this orchestration's results → recalculate `.orchestrator/metrics.md` (duration per story/batch/run from `events/` timestamps, tokens/tool_uses from what the `Agent` tool returned when each subagent completed) → report the final summary to the user.
16. **Phase 6 — Post-closure correction**: ask the user whether they want to request a change on any already-`finalized` story (see the "Reputation and post-closure correction" section above). Repeat until they say no; only then re-run the trial-merge and close for good.

**Resumption**: if, at the start of an orchestration run, the board shows stories with a status other than `finalized`/`aborted`, there is an interrupted execution — it is resumed, not restarted: reconstruct context from events + `designs/` + `git -C workspace/<base-repo> worktree list` + real diffs (git is the source of truth), relaunch only the incomplete agents in `RESUMED` mode on their existing worktrees (never recreate them), and reassemble the queue of pending batches.

**Dry-run mode** (`/legion dry-run`): runs through the end of the first batch's gate (including DECs and migration names/order) but does NOT send the approvals — the designs are persisted as reviewable files in `.orchestrator/designs/<Story-ID>.md` (status `PENDING APPROVAL`) and the orchestrator presents the index with links, along with the **complete batch plan** (all stories, not just the first batch). The user reviews them (can annotate them directly in the file) and decides **per story**: approve (with or without adjustments) or discard (the worktree is empty — Stage A doesn't write code — it gets removed and that story ends up `aborted`). After the user approves each design, and before the approval reaches the implementer, the `design-reviewer` agent audits the approved design against the base repo (loop: amend → re-review, no fixed cap; the user can omit each round's findings or disable the loop for the run — omitted findings stay recorded in the design's `## Design review` section and are always passed to `worktree-reviewer`'s "Assumed residual risks" section). A cheap human checkpoint: designing costs a fraction of implementing.

## Quality gate (non-negotiable)

- **Adversarial reviewer**: no `FINALIZED` is valid without the `APPROVED` verdict from `worktree-reviewer`, which includes the manual audit of the architecture rules registered in `config.md`.
- Do not assume tools or checks that are not confirmed in `config.md` or in the base repo's real rules (e.g.: do not invent an architecture test that doesn't exist in the destination repo).

## Hard rules for the Orchestrator

- **Never** edit code inside a worktree: every modification is executed by that story's agent under the orchestrator's order. (Creating/removing worktrees is infrastructure and IS the orchestrator's job.)
- **Explicit exceptions to "an agent only writes in its own worktree"** (besides `.orchestrator/`, an exclusive zone of the Orchestrator itself):
  - `worktree-agent-docs` READS from its worktree but WRITES to `docs/<base-repo>/` (root of this orchestrator), always in Markdown — that's its only write zone.
  - `worktree-agent-data` writes the migration itself **inside its worktree** (the project's migration tool needs to find it there), but any auxiliary transformation/backfill/manual rollback script goes in `scripts/<base-repo>/` (root of this orchestrator), outside the worktree.
  - No other implementing agent writes outside its worktree.
- **Never** commit, push, or create PRs, nor allow an agent to do so. The work remains uncommitted in each worktree; the user harvests it.
- **Never** remove a worktree with uncommitted changes (except for a discard confirmed by the user).
- An agent **never** works outside its worktree nor communicates directly with another (never `SendMessage` between agents); every coordination decision goes through the orchestrator. **Sole exception**: an agent may write a Signal or an Announcement in `.orchestrator/` — that is depositing information into the shared environment, not direct communication between worktrees, and it never replaces or bypasses the orchestrator's approval for anything.
- Every architectural decision is recorded in `.orchestrator/decisions/DEC-NNN.md` with: context, alternatives compared, criteria evaluated, decision, and orders issued.

## Synchronization between stories

Goal: **a single way of solving the same problem across all branches**.

Synchronization is **preventive first, corrective second**:
- **Preventive**: the overlap pre-analysis and the batch plan avoid running stories that step on each other in parallel without coordination; the per-batch design gate unifies approaches before code is written; and `components.md` + the `designs/` from previous batches act as architectural memory that keeps an agent from reinventing something another story already solved (mandatory lookup + replication of the reference implementation — the agent may READ the specific file cited as `Reference` in another worktree, the sole exception to isolation).
- **In real time, within a batch in progress**: Signals and Announcements (see above) cover what the gate can't — something discovered halfway through Stage B, while other stories in the same batch are already running and the next gate is still far off.
- **Corrective**: whatever neither the gate nor the Signals/Announcements anticipated is detected by monitoring the events and is corrected with migration orders.

For every reported creation/modification event, compare it against the events of other active or already-finalized stories. Look for functional equivalences even if the component type differs. This applies to any reusable component: utilities, services, helpers, DTOs/types, mappers, configurations, validators, repositories/data access, shared classes or modules, and package structures.

### Conflict resolution process

When two agents solve similar problems with different approaches:

1. Read both implementations (Read over the reported files).
2. Evaluate **reuse** (which one allows sharing more logic?).
3. Evaluate **maintainability** (coupling, clarity, tests).
4. Evaluate **simplicity** (fewer layers/indirection for the same result).
5. Evaluate **alignment with the existing architecture** of the destination project (rules registered in `config.md`).
6. Apply the `.claude/skills/patterns-and-smells/SKILL.md` guide as a tie-breaker — if neither implementation complies, order both stories to do it the right way.
7. Select the best alternative and document it in `.orchestrator/decisions/`.
8. Order the corresponding agent to adopt that solution via `SendMessage`, citing the decision. If the story already finalized, `SendMessage` continues it with its context anyway and reopens the review.

## Execution mechanics (Claude Code tools)

- **Launch agents**: `Agent` tool with `subagent_type` resolved by `.orchestrator/capabilities.md` (default `"worktree-agent"` if no specialization applies), one call per story in the active batch, all in the same message so they run in parallel, `run_in_background: true`. For stories with `## Subtasks`, each agent in the sequence is launched only once the previous one reaches `FINALIZED`, never in the same message.
- **Continue/order an agent**: `SendMessage` with the agent's ID/name (keeps its context). Used for migration orders and status requests.
- **Monitoring**: re-read `.orchestrator/events/*.md` upon receiving each subagent notification; between notifications, use `Monitor` on the events folder if there's a long wait.
- **End of execution**: only when the queue is empty, every story has its `FINALIZED` event, all migration orders were executed, and the closing trial-merge passed.

## Applying this system to a new project

This system does not assume any particular language, framework, or build tool. To use it on a different repository:

1. Clone **a single** destination repo inside `workspace/` (e.g. `workspace/base-repo/`) — a single clone, the orchestrator automatically creates the worktrees per story.
2. Run `/legion` — if `.orchestrator/config.md` has unfilled placeholders, the orchestrator investigates the repo and asks whatever is missing before starting.
3. If the destination project has its own documented pattern/code-smell conventions, reference them from `.claude/skills/patterns-and-smells/SKILL.md` instead of duplicating them; if it doesn't have them, the guide helps you inventory them for the first time.
